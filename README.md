# BTT

Приложение для регистрации перевозчиков, просмотра рейсов и бронирования билетов.

## Стадии разработки

1. **Модель и контракты.** Миграции PostgreSQL, JPA-сущности, OpenAPI и BPMN.
2. **Регистрация перевозчиков.** Права представителей и исполнителей, переходы заявлений, решения и история свидетельств.
3. **Перевозки и билеты.** Каталог и расписание рейсов, доступность мест, бронирование и отмена.

## Первая стадия

- [ER-диаграмма](btt-domain-logic-module/er/er.svg) описывает 13 сущностей и две таблицы связей. Flyway применяет три [миграции](btt-domain-logic-module/src/main/resources/db/migration). Hibernate сверяет схему с [JPA-моделью](btt-domain-logic-module/src/main/java/com/github/evseevda/domainlogicmodule/entity) при запуске.
- [OpenAPI](btt-api/btt-api-domain-logic/src/main/resources/openapi/api.yaml) задаёт операции под `/api/v1`, тела запросов, DTO и ошибки. Maven генерирует интерфейсы Spring и DTO в модуле `btt-api-domain-logic`. Контроллеры реализуют эти интерфейсы и возвращают HTTP 501 с пустым телом для корректных запросов.
## Подключение организаций

Аккаунты обычных пользователей и сотрудников портала создаются через `POST /api/v1/users`. Для назначения ролей сотрудника требуется отдельное разрешение у вызывающего пользователя. Подключение организации и присоединение к ней оформляются отдельными заявками после создания аккаунта.

- [Подключение организации к порталу](btt-domain-logic-module/bpmn/blm_organization_registration_v1.bpmn). Администрация проверяет реквизиты существующего юридического лица и полномочия заявителя. При одобрении создаются запись организации и связь с первым уполномоченным представителем.
- [Присоединение сотрудника к организации](btt-domain-logic-module/bpmn/blm_organization_membership_v1.bpmn). Решение принимает уполномоченный представитель выбранной организации. Подтверждение даёт членство. Полномочия представителя делегируются отдельно.

В каждой схеме бэкенд запускает процесс по BPMN ID с переменной `requestId`. Решение из формы передаётся сообщением с тем же ключом корреляции. Для маршрутизации используется булево поле `approved`. Обработчик сохраняет решение и проверяющего, а при отказе — причину. Контракты этих заявок, хранение данных и обработчики Zeebe относятся к реализации.

## Процессы регистрации перевозчика

| Техническая схема Camunda 8 | Кто подаёт заявление | Что происходит после согласования положительного решения |
| --- | --- | --- |
| [Первичная регистрация](btt-domain-logic-module/bpmn/blm_initial_registration_v1.bpmn) | Представитель организации | Создаются активный перевозчик, РУ, их первые версии и записи лицензий. |
| [Изменение регистрации](btt-domain-logic-module/bpmn/blm_registration_amendment_v1.bpmn) | Представитель организации | Создаётся новая версия РУ со ссылкой на новую версию перевозчика. Лицензии записываются заново, включая неизменённые. Вид транспорта может измениться. Организация закреплена за перевозчиком. |
| [Отмена по инициативе перевозчика](btt-domain-logic-module/bpmn/blm_carrier_cancellation_v1.bpmn) | Представитель организации | Перевозчик становится неактивным. Создаётся новая версия РУ со снимком перевозчика и лицензий. Прежняя версия РУ аннулируется и остаётся доступна в истории. |
| [Отмена по инициативе администрации](btt-domain-logic-module/bpmn/blm_admin_cancellation_v1.bpmn) | Сотрудник администрации | Действуют те же правила версий и аннулирования. |

Во всех четырёх процессах заявление можно взять в работу или назначить исполнителю. Исполнитель передаёт решение на согласование. Согласующий может согласовать положительное решение или отказ либо вернуть решение на доработку тому же исполнителю. Сотрудник с обоими разрешениями может выполнить оба этапа. Пока решение не согласовано, заявление может отозвать только пользователь, который его подал. Регистрация пользователя, бронирование и отмена бронирования остаются операциями API.

При подаче заявления бэкенд запускает нужный процесс по его BPMN ID и передаёт `requestId` как переменную процесса. Все схемы начинаются с обычного Start Event. Для последующих ожиданий используются BPMN-сообщения с ключом корреляции `requestId`. Имена сообщений собраны в [BpmnEventNames.java](btt-domain-logic-module/src/main/java/com/github/evseevda/domainlogicmodule/workflow/BpmnEventNames.java). Префикс разрешений зависит от процесса. `.decide` разрешает взять заявление и вынести решение, `.approve` — согласовать или вернуть, `.assign` вместе с `.decide` — назначить другого исполнителя с разрешением `.decide`. Роль начальника может объединять эти разрешения по всем четырём процессам.

Миграции, JPA и OpenAPI пока описывают предыдущий этап проекта. При реализации потребуется добавить версии перевозчика и лицензии в снимках, привязку версии РУ к версии перевозчика, команды взятия в работу, согласования и возврата. Правила авторизации и переходов проверяются на бэкенде. Решение по конкретной редакции, итоговый статус и изменения перевозчика и РУ фиксируются транзакционно.

## Проектные допущения

- Связи и типы исходят из ER. Уникальность логина, почты, названий справочников, ИНН, ОГРН, номера билета и номера свидетельства, а также обязательность полей уточнены для первой схемы. Длительность маршрута задана в минутах. Временные отметки сохраняются как локальное время без смещения UTC.
- Сущности и enum находятся в предметных пакетах `domain`, JPA-конвертеры — в соседних `conversion`. Коды статусов перевозчика, лицензии и рейса приняты как проектные допущения и перечислены в OpenAPI.
- Регистрация пользователя создаёт профиль. Способ аутентификации, подтверждение почты и назначение ролей предстоит определить.
- При бронировании пассажир определяется по текущему пользователю, номер и цена формируются на сервере. Проверка доступности, защита от одновременного бронирования одного места и правила расчёта цены относятся к реализации.
- В списках `limit` и `offset` применяются после фильтрации. Права на просмотр чужих профилей, заявлений и билетов предстоит определить вместе с правилами авторизации.

## Сборка

Из корня `btt` выполните `mvn compile`. Профиль `local` подключается к PostgreSQL из Docker Compose. Для запуска без профиля `local` с внешней БД задайте `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` и `SPRING_DATASOURCE_PASSWORD`. При старте Flyway применяет миграции, затем Hibernate проверяет схему.

### Локальная база PostgreSQL

Из корня `btt` запустите PostgreSQL и приложение с подключением к базе `btt_business_logic_module_db`:

```sh
docker compose -f btt-domain-logic-module/docker-compose/docker-compose.yaml up -d --wait postgres
mvn package
java -jar btt-domain-logic-module/target/btt-domain-logic-module-0.0.1-SNAPSHOT.jar --spring.profiles.active=local
```

После запуска приложения историю миграций можно посмотреть из второго терминала:

```sh
docker compose -f btt-domain-logic-module/docker-compose/docker-compose.yaml exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank"'
```

Контейнер хранит данные в именованном томе. Порт на хосте по умолчанию — `5433`.

### Моковые контроллеры

Для локальной проверки заглушек соберите приложение командой `mvn package` из корня `btt`:

```sh
java -jar btt-domain-logic-module/target/btt-domain-logic-module-0.0.1-SNAPSHOT.jar --spring.profiles.active=mock-api
curl -i http://127.0.0.1:8080/api/v1/trips
```

Профиль `mock-api` запускается без PostgreSQL, отключает обнаружение сервисов и открывает маршруты `/api/v1/**` для локальных запросов без аутентификации.
